# team-change（Antigravity）

> 正本: `.agent/skills/team-change/SKILL.md`（英語）。
> Claude Code 版: `.claude/skills/team-change/SKILL.md`（Agent Teams）。フェーズと成果物は同じで、ここではチームの代わりにリードがサブエージェントを統率する。

## 目的

**不具合報告または変更依頼** を受け取り、作業ブランチ上でレビュー可能な状態まで進めます: 調査・設計 → 仕様書更新 → 実装 → 責任者チェック。**メインセッション（あなた）がリードであり、オーケストレーター** です: `.agent/agents/` に定義されたサブエージェントを `invoke_subagent` で起動し、それぞれに必要な情報をすべて渡し、結果を集約します。

単なる「直して」との違いは次の 2 点です。

- **仕様書が先。** 変更後の挙動を `specs/<feature>/spec.md` に書いてから、ソースファイルに手を付けます。コードはその仕様書に対して実装します。
- **このスキルの中ではレビューしない。** レビューは **別セッション** で、この checkout に対する `/git-pr-cross-review working`（`develop` との差分。未コミットの変更を含む）で行います。このスキルは、そのコマンドをそのままユーザーに渡して終了します。commit・push・PR は、そのレビューの **後** に、それぞれユーザーの了承を得て行います（`.agent/rules/common-git-workflow.md` 参照）。

対象: **意図が明確な不具合修正と、小〜中規模の機能変更。** 要件が固まっていないものや、複数コンポーネントにまたがる大規模作業は対象外です。

> **Antigravity には共有タスクリストがない。** サブエージェントは互いの状態を見られない。結果が集まる場所はあなただけなので、サブエージェントが必要とするコンテキスト（依頼内容・調査結果・仕様書サマリー・制約）は、すべてそのプロンプトに直接書いて渡すこと。

## ユーザー入力

依頼は引数として、次のいずれかの形で渡されます。

- **不具合報告**（症状・再現手順・期待する挙動など、分かっている範囲）
- **変更依頼**（何を変えるか・期待する挙動・対象モジュールを文章で）
- **既存の仕様書のパス**（`specs/<feature>/spec.md`）と、そこに加える変更

### 引数チェック

引数が空の場合は以下を表示して **中断** する。

```
エラー: 修正したい不具合、または変更したい内容を記述してください。

使い方:
  /team-change <不具合の内容 または 変更内容>

例:
  /team-change 三角形の頂点色が Rust 版だけ反転して表示される
  /team-change ウィンドウのリサイズに追従してスワップチェーンを再生成する
  /team-change specs/003-swapchain-resize/spec.md に最小化時の挙動を追加する
```

**依頼が無い場合は、絶対にサブエージェントを起動しないこと。**

### 依頼が曖昧な場合

依頼から挙動が一意に決まらない場合（重要な分岐が未定義、不具合の期待挙動が不明など）は **推測しない**。不明点を整理してユーザーに確認する（`.agent/rules/common-answer-policy.md` 参照）。仕様書に推測を書かないために、仕様書を書く前に行う。

## 前提・制約【厳守】

サブエージェントは `AGENTS.md` を読みますが、確実に守らせるため、**各サブエージェントのプロンプトに以下の制約を必ず明記** してください。

- **編集可能範囲**: ファイルの作成・編集は `AGENTS.md` の「作業範囲ルール」で許可されたパス以下に限定する。それ以外は `coding-harness` プラグインの `PreToolUse` フックが拒否する。`specs/` はその範囲内。範囲外の修正が必要と判明した場合は、修正せずユーザーに確認する。
- **仕様書が先**: フェーズ 2 の仕様書更新が完了して報告されるまで、ソースファイルを編集しない。仕様書と矛盾するコードは近道ではなく欠陥として扱う。
- **コーディング規約**: 実装はすべて `.agent/rules/` 配下の規約（`common-coding-style.md` / `cpp-coding-style.md` / `rust-coding-style.md` 等）に準拠する。
- **シンプルさ最優先**: 共通規約の KISS / YAGNI に従い、仕様を満たす最小限の変更に留める。
- **言語**: ドキュメント・コメント・仕様書本文・ユーザーへの報告はすべて日本語で行う。
- **編集者は 1 体に限定**: ファイル競合を避けるため、**実際にファイルを編集するのは `implementer` サブエージェントのみ**（仕様書も含む）。`investigator` はプロンプトで読み取り専用を指示し、結果を返すだけとする。
- **Git のルール**: 作業ブランチで作業し、`develop` と `main` には直接コミットしない。`.agent/rules/common-git-workflow.md` に従い、push はブランチ名をユーザーに示して了承を得てからにする。強制 push・リモートブランチの削除・マージは行わない（いずれにせよ `scm-guard` が拒否する）。

> **Antigravity のサブエージェントには、文書化された「読み取り専用」実行モードがない。** 読み取り専用はエージェント定義に「ファイルを一切編集しない」と書くことと、編集範囲フックとで担保している。そのため、**`investigator` のプロンプトには必ず「ファイルを一切編集しない」を改めて明記すること**。

## サブエージェント

| サブエージェント | 役割 | 編集 |
|----------------|------|------|
| `investigator` | 不具合: 根本原因と影響範囲を特定。機能変更: 対象コード・実装方針・対象ファイルを特定。あわせて更新すべき仕様書を特定する | 読み取り専用 |
| `implementer` | 仕様書を更新し、調査結果に沿って変更を実装し、ビルド・テストを実行する（**唯一の編集者**） | 編集可（範囲限定） |

フェーズ 4 の最終チェックと、フェーズ 5 のマニュアル生成・引き渡しは **リード（あなた）自身** が行う。レビュアーのサブエージェントは起動しない。

**順序**: `調査` → `仕様書更新` → `実装` → `責任者チェック` → `マニュアル生成・引き渡し`

## ワークフロー

各フェーズの開始時に、現在のフェーズ名を 1 行でユーザーに表示する。

### フェーズ 0: 準備

リードとして、checkout が短命なブランチにあることを確認する（無ければ現在の `develop` から `feature/<name>` を作る。`<name>` は英小文字 2〜4 語を `-` でつないだもの）。`.agent/rules/common-git-workflow.md` の「Start and Finish of a Task」に従う。

### フェーズ 1: 調査・設計

**`investigator`** サブエージェントを `invoke_subagent` で起動する。プロンプトには、依頼内容をそのまま、上記の制約、そして次の指示（編集禁止）を含める:

- **不具合**: 症状に関連するコードを特定し、根本原因（どのファイルの・どの処理が・なぜ誤っているか）を突き止める。影響範囲を洗い出す。
- **機能変更**: 現在の挙動を実装しているコードを特定し、実装方針を決め、対象ファイルを列挙する。影響範囲（呼び出し元・関連モジュール・`cpp/` と `rust/` の両方に同じ機能がある場合はもう一方の移植）を洗い出す。
- **仕様書の特定**: この機能を扱う仕様書を探す。
  - `specs/*/spec.md` を機能名（モジュール名・依頼中のキーワード）で検索する。
  - 既存の仕様書があれば、そのパスと変更すべきセクションを報告する。
  - 無ければ、新規ディレクトリ `specs/<NNN>-<short-name>/` を提案する。`NNN` は `specs/` 配下の最大番号 + 1（`specs/` が空または存在しない場合は `001`）、`<short-name>` は英小文字 2〜4 語を `-` でつないだもの（例: `003-swapchain-resize`）。`.specify/scripts/bash/create-new-feature.sh` は **実行しない**（フェーズ 0 で既にブランチを作っており、スクリプトはもう 1 本作ってしまうため）。
- 以下を構造化して返す: `根本原因 / 実装方針`（ファイルパス:行番号 + 説明）／ `関連箇所` ／ `対象ファイル` ／ `仕様書の対象`（パス、既存か新規か、変更するセクション）。

> 根本原因が特定できない（不具合）、または方針が未決事項に依存する（機能変更）場合は推測しない。確定した事実と不明点を整理してユーザーに報告し、中断する。

### フェーズ 2: 仕様書更新

**`implementer`** サブエージェントを仕様書のみを対象に `invoke_subagent` で起動する（ソースファイルはまだ触らない）。プロンプトには、依頼内容・調査担当の結果・制約と、次を含める:

- **既存の仕様書**: `specs/<feature>/spec.md` を、変更 **後** の挙動を表すように編集する。該当するユーザーストーリー・受け入れシナリオ（`Given / When / Then`）・機能要件を更新する。不具合の場合は、その不具合が違反していた受け入れシナリオ（本来それで検出できたはずのもの）を追加または修正する。
- **新規の仕様書**: `.specify/templates/spec-template.md` から `specs/<NNN>-<short-name>/spec.md` を作成する。依頼から確定できる内容だけを埋め、不明な点は `[NEEDS CLARIFICATION: ...]` と記して報告する（勝手に埋めない）。
- 仕様書には **何をする挙動か** を書く。実装方法（ファイル名・型名）は書かない。
- 「仕様書サマリー」を返す: 仕様書のパス、新規か既存か、変更したセクション（それぞれ変更前 → 変更後を 1 行で）。

> 仕様書を書く過程でフェーズ 1 が見落とした曖昧さが見つかったら、ここで止めてユーザーに確認する。曖昧な仕様のままコードに進まない。

### フェーズ 3: 実装

**`implementer`** サブエージェントを `invoke_subagent` で再度起動する。プロンプトには、依頼内容・調査担当の結果・仕様書サマリー・制約と、次を含める:

- 調査結果の方針に従い、更新した仕様書を満たす最小限の変更を編集可能範囲内で行う（シンプルさ最優先、規約厳守）。
- ビルド・テストによる検証:
  - プロジェクトのビルドを実行する（`rust/` は `cargo build` / `cargo test`、`cpp/` はプロジェクトが定める CMake またはコンパイラーの呼び出し）。エラーがあれば修正する。
  - ロジックを変更した場合は、対応するユニットテストを作成・実行する。
  - 自動ビルドの手段が無い場合はその旨を明示し、規約準拠と整合性の静的チェックで代替する。
- 変更ファイル・変更内容・期待される効果を「変更サマリー」として返す。

### フェーズ 4: 責任者チェック

リード（あなた）自身が読み取り専用で行う。

**(1) 依頼 → 仕様 → コードの整合確認**

- 元の依頼、仕様書サマリー、変更サマリーを読み直す。
- 項目ごとに確認する:
  - 仕様書は依頼どおりの内容を過不足なく記述しているか
  - コードは仕様書を実装しているか（変更した受け入れシナリオごとに対応するコード変更があるか）
  - 指示にない余計な変更（コード・仕様書とも）が紛れ込んでいないか
- 不一致があれば **ハードブロック（差し戻し）**。

**(2) 影響範囲の最終確認**

- 変更ファイルの呼び出し元・依存関係を確認する。
- 他の箇所に意図しない挙動変更が入っていないか確認する。
- 問題があれば **ハードブロック（差し戻し）**。

**ハードブロック時**:

- 差し戻し理由を明示し、修正指示（仕様書・コード・または両方）を付けて `implementer` を `invoke_subagent` で再度起動する。
- 修正後、このフェーズを再実行する（最大 2 周）。
- 2 周で収束しない場合は、残った問題をユーザーに報告して中断する。

### フェーズ 5: マニュアル生成・レビュー引き渡し

責任者チェックが通ったら:

1. **変更マニュアルを生成** して保存する（下記の仕様）。
2. **引き渡し**: 保存先パス・要点・**この checkout の新しいセッション** で実行するレビューコマンド `/git-pr-cross-review working` を提示する。この引き渡しをもって作業は完了。変更は未コミットのまま残す: `.agent/rules/common-git-workflow.md` のとおり、commit・push・PR はレビューの後、それぞれユーザーの了承を得て行う。ここでは commit も push もしない。スキルの途中でユーザーに求められた場合は、先にレビューを案内する。

**マニュアルの出力仕様**:

- 保存先: `docs/manuals/`（無ければ作成）。
- ファイル名: `<変更した概要>_<YYYYMMDD-HHMMSS>.html`（実際のタイムスタンプを使う。`date` コマンド等）。
  - `<変更した概要>` は変更内容を要約した短い日本語（20 文字以内を目安）。
  - ファイル名に使えない文字（`\ / : * ? " < > |`）とスペースは使わない。区切りが必要なら `-` を使う。
  - 例: `Rust版の頂点色反転を修正_20260918-153000.html`
- 形式: CSS を `<style>` に埋め込んだ単一の HTML（外部参照なし）。ブラウザーで直接開ける。
- 文字コード: UTF-8（`<meta charset="UTF-8">` を必ず含める）。言語属性は `<html lang="ja">`。
- 保存先はこのパスのみ（`docs` 配下なので編集可能範囲内）。マニュアルは **コミットしない**（ローカルの成果物）。

**マニュアルの内容**（この見出し構成を HTML で表現する）:

- 変更内容: 依頼内容 ／ 根本原因または実装方針 ／ 変更ファイル一覧（仕様書を含む。ファイルごとの変更概要付き）。
- 仕様書の更新: 仕様書のパス（新規か既存か）と、変更したセクションごとの変更前 → 変更後。
- 責任者チェックの結果: 整合確認（依頼 → 仕様 → コード）と影響範囲。
- 動作確認手順: ユーザーが実際に確認すべき手順とポイント（不具合の場合は再現しないことの確認方法を含む）。仕様書の受け入れシナリオから導く。
- レビュー依頼: 引き渡し。レビューは別セッションで行うことを明記し、(1) 作業ブランチと変更ファイル（未コミット）、(2) この checkout の新しい Antigravity セッションで `/git-pr-cross-review working` を実行する、(3) レビューが通ったら、それぞれユーザーの了承を得て commit・push・`develop` をベースとした PR 作成を行う、を示す。
- 注意事項・リスク: 影響範囲や潜在的なリスクがあれば記載。
- 残課題: 未対応の事項や `[NEEDS CLARIFICATION]` があれば記載。

**HTML テンプレート**: Claude Code 版（`.claude/skills/team-change/SKILL.md` の「HTML template」）と同じ骨組みを使い、レビューコマンドを `/git-pr-cross-review working` に、文言を「この checkout の新しい Antigravity セッションで次を実行する」に置き換える。

## 最終報告

次の順で提示する。

1. 生成した HTML マニュアルの保存先パス。
2. 仕様書のパスと、変更内容の 1 行要約。
3. 作業ブランチと、変更したソースファイル（未コミット）。
4. レビュー引き渡し（そのまま実行できる形で）: この checkout の新しいセッションで `/git-pr-cross-review working` を実行する。commit・push・PR はそのレビューの後であることを明記する。

残課題やその他の補足は末尾に添える。

## 注意事項

- **このスキルはレビューしない。** レビュアーのサブエージェントを起動せず、`/git-pr-cross-review` もここでは実行しない。別セッションがレビューである。分けることでレビューの独立性を保つ。
- **`implementer` サブエージェントだけが編集者**（ソースファイルも仕様書も）。`investigator` には編集させない（ファイル競合防止）。
- **仕様書が先。** 仕様書サマリーの報告前に実装担当がソースファイルに着手したら止めて、フェーズ 2 に戻す。
- サブエージェントへのプロンプトはすべて自己完結させる: Antigravity には共有タスクリストがないので、プロンプトに書かなかったものは、そのサブエージェントにとって存在しない。
- 編集可能範囲外の変更が必要になった時点で中断し、ユーザーに確認する。
- **このスキルでは commit も push もしない。** どちらもレビューの後、それぞれユーザーの了承を得て行い、push はユーザーがブランチ名を見た後にだけ行う。強制 push・リモートブランチの削除・PR のマージは行わない。
- 不確かな点を断定しない。報告では確定した事実と不明点を分けて示す（`.agent/rules/common-answer-policy.md` 参照）。
