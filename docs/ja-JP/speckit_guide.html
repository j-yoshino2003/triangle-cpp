spec-kit — 使い方ガイド

対象: Claude Code のみ。spec-kit のスラッシュコマンドは .claude/commands/speckit.*.md にしか無く、 Codex CLI / Antigravity CLI には入っていない。他のエージェントから使うときは節 7 の scripts/speckit を直接呼ぶ。

1. これは何 / /team-change との使い分け

spec-kit は「自然言語の要望 → 仕様書 → 計画 → タスク → 実装」を 1 機能ずつ回すコマンド群です。 生成物は specs/<NNN-short-name>/ に溜まります。

ハーネスの /team-change と範囲が重なるので、先に使い分けを決めてください。

使うもの向いている場面
/team-change既にある機能の不具合修正・仕様変更。調査 → 仕様書更新 → 実装 → 責任者チェックが 1 回のループで終わる。仕様書は既存の specs/<feature>/spec.md を書き換える
/speckit.*新しい機能をゼロから起こす。仕様を詰めてからコードに入りたい。工程がコマンドに分かれているので、途中で止めて人が確認できる

どちらも書き込み先は specs/ で同じです。片方で作った仕様書をもう片方が更新しても問題ありません。

2. 最初に 1 回だけ: /speckit.constitution

ここを飛ばすと下流が空回りします。 .specify/memory/constitution.md は spec-kit のプレースホルダーテンプレートのままです （導入先で埋める前提。リポジトリの CLAUDE.md 参照）。下流のコマンドがこのファイルを読みます。
  • /speckit.plan は constitution を読み（speckit.plan.md 手順 2）、計画の Constitution Check 節をそこから埋める（同 手順 3）
  • /speckit.analyze は constitution を「非交渉（non-negotiable）」として扱い、違反を自動的に CRITICAL にする（speckit.analyze.md の Constitution Authority）
つまり未記入のままだと、計画の Constitution Check は空のテンプレートを参照し、analyze の一番強いゲートが一度も発火しません。 
/speckit.constitution

プロジェクトに 1 回で済みます。原則を変えたいときだけ再実行します（このコマンドは .specify/templates/ 側の依存テンプレートも合わせて同期します）。

3. 標準フロー

/speckit.constitution   ← プロジェクトに 1 回だけ
      ↓
/speckit.specify → /speckit.clarify → /speckit.plan → /speckit.tasks → /speckit.analyze → /speckit.implement
                                           ↓                ↓
                                  /speckit.checklist   /speckit.taskstoissues（任意）
/speckit.analyze は /speckit.tasks の後です。 spec.md / plan.md / tasks.md の 3 つを突き合わせる点検なので、 check-prerequisites.sh --require-tasks を通して走ります。tasks.md が無いと そこで止まります。
コマンド役割作る / 更新するもの
/speckit.constitutionプロジェクトの原則を作る・更新する。依存テンプレートも同期する.specify/memory/constitution.md
/speckit.specify自然言語の要望から仕様書を作る。ブランチも切る（節 5）specs/<NNN-short-name>/spec.md
/speckit.clarify仕様の穴を最大 5 問の的を絞った質問で埋め、回答を仕様書へ書き戻すspec.md を更新
/speckit.plan仕様書と constitution から設計を起こす。Phase 0 で調査、Phase 1 でデータモデル・契約・クイックスタート。再実行すると plan.md がテンプレートで上書きされる（節 6）plan.md、必要に応じて research.md / data-model.md / contracts/ / quickstart.md、ルートの CLAUDE.md（節 6）
/speckit.analyzespec.md / plan.md / tasks.md の整合を非破壊で点検する。constitution 違反は自動 CRITICAL（レポートのみ。ファイルは書き換えない）
/speckit.checklist「英語の単体テスト」として機能ごとのチェックリストを作る。ドメインごとに別ファイル（ux.md / api.md など）で、既存ファイルは上書きせず追記するspecs/<NNN-short-name>/checklists/<type>.md
/speckit.tasks設計から依存順に並んだ実装タスクを起こすtasks.md
/speckit.taskstoissuesタスクを GitHub の issue に変換する（任意）GitHub の issue（節 7 の注意）
/speckit.implementtasks.md のタスクを実行する。手順 10 に SCM の開始と終了が組み込まれている（節 8）ソースコード

4. 規模別の使い分け

規模流れ
小（既存コードの微調整）/team-change で足りることが多い。spec-kit を使うなら specify → plan → implement
普通の機能specify → clarify → plan → tasks → implement
複雑（複数モジュール・状態機械・非同期）specify → clarify → plan → tasks → analyze → implement。受け入れ条件が多いなら plan の後に checklist

clarify を飛ばすと後で効きます。特に状態遷移・データの持ち主・所有権と寿命は、 仕様で決めずに実装に入ると書き直しになります。

5. ブランチ名の衝突（一番つまずく所）

spec-kit の命名規約とこのプロジェクトの git-flow は噛み合いません。仕組みから説明します。

  • /speckit.specify は .specify/scripts/bash/create-new-feature.sh を呼び、その中で git checkout -b <NNN>-<short-name> を現在の HEAD から実行する（例: 001-swapchain-resize）
  • 一方 .claude/rules/common/git-workflow.md は「develop から切った feature/<name>」「develop / main に直接コミットしない」と定めている
  • さらに .specify/scripts/bash/common.sh の check_feature_branch() は、現在のブランチ名が ^[0-9]{3}- に一致しないと ERROR: Not on a feature branch で exit 1 する。 これを呼ぶのは setup-plan.sh と check-prerequisites.sh で、 /speckit.specify 以外のすべてのコマンドがそのどちらかを通る。つまり feature/<name> に居ると /speckit.clarify 以降が全部止まる （clarify / tasks / analyze / checklist / implement / taskstoissues が check-prerequisites.sh、plan が setup-plan.sh）。 節 3 のフロー図で plan より前に居る clarify が最初の関門になる

逃げ道は環境変数 SPECIFY_FEATURE です。common.sh の get_current_branch() は git より先に SPECIFY_FEATURE を見るので、ブランチ名と仕様フォルダー名を切り離せます。

運用 A: プロジェクトの命名を守る（推奨）

【Claude Code で】 develop に居ることを確認してから（新しいブランチは現在の HEAD から切られる）
/speckit.specify ウィンドウのリサイズに追従してスワップチェーンを再生成する
→ 001-swapchain-resize が作られて checkout される

【Claude Code で】 プロジェクトの命名に付け替える
git switch -c feature/swapchain-resize

【Claude Code を終了し、シェルで】 環境変数を設定してから Claude Code を起動し直す
export SPECIFY_FEATURE=001-swapchain-resize
claude

【Claude Code で】 以降は普通に進める
/speckit.clarify
/speckit.plan

specs/ のフォルダー名は 001-swapchain-resize のままなので、環境変数がそれを指します。 PR のベースは develop、ブランチ名は規約どおり、spec-kit のスクリプトも通ります。

export はシェル側で、Claude Code を起動する前に行います。 スクリプトを実際に起動するのは Claude Code の Bash 子プロセスなので、その親シェルに入っていないと効きません。 1 機能ごとに値が変わるため settings.local.json の env には置けません。

機能を切り替えたら値も貼り替えること（終わったら unset SPECIFY_FEATURE）。 この値は一切検証されません。get_current_branch() は値をそのまま返し、 check_feature_branch() は ^[0-9]{3}- の形だけを見て、 find_feature_dir_by_prefix() は 3 桁番号の前方一致でフォルダーを解決します。 2 本目の機能に移ったのに 001-... が残っていると、/speckit.plan 以降がすべて specs/001-.../ を対象に動き、エラーも警告も出ません。 plan の無条件上書き（節 6）と重なると、1 本目の計画書が黙って空テンプレートに戻ります。 現在の対象は scripts/speckit check --paths-only の FEATURE_DIR で確認できます。

運用 B: spec-kit の命名に寄せる

001-swapchain-resize のまま最後まで進めます。環境変数は要りませんが、ブランチ名が feature/<name> 規約から外れます。後から名前を直すには切り直しが必要で、 scm-guard が強制 push とリモートブランチ削除を拒否するため、push 済みだと手間が増えます。

6. 生成物の置き場所

パス作るコマンド元テンプレート
.specify/memory/constitution.md/speckit.constitution—
specs/<NNN-short-name>/spec.md/speckit.specify.specify/templates/spec-template.md
specs/<NNN-short-name>/plan.md/speckit.plan（毎回上書き）plan-template.md
specs/<NNN-short-name>/tasks.md/speckit.taskstasks-template.md
specs/<NNN-short-name>/checklists/*.md/speckit.checklist（既存は追記）checklist-template.md
research.md / data-model.md / quickstart.md / contracts//speckit.plan（必要に応じて）—
ルートの CLAUDE.md/speckit.plan の手順 3（update-agent-context.sh claude）agent-file-template.md（無ければ新規作成）

/speckit.plan の再実行は plan.md をテンプレートで上書きします。 setup-plan.sh は存在確認もバックアップもせずに cp するので、Technical Context・ Constitution Check の判定・Phase 0 / 1 の成果など書き足した内容は警告無しに消えます。 analyze の指摘を受けて plan を回し直す前に、commit するか退避してください。 /speckit.checklist が既存ファイルを上書きしないのと対照的です。

ルートの CLAUDE.md は作業範囲の外です。 /speckit.plan の手順 3 は update-agent-context.sh claude を実行し、 $REPO_ROOT/CLAUDE.md に書きます（無ければ新規作成）。このハーネスは CLAUDE.local.md → @AGENTS.md 構成でルートに CLAUDE.md を置かないため、 新規作成される側です。AGENTS.md の許可リストと 3 つの ALLOW_PATTERNS は CLAUDE.local.md しか持たず、edit-scope-guard のフックも Edit / Write / NotebookEdit しか見ないので、Bash 経由のこの書き込みは検査されません。 できたファイルは Claude Code が毎セッション自動読み込みするため、作業ルールが二重に並びます。 手順 3 を実行させたくないときは /speckit.plan にそう指示してください。

specs/ と .specify/ は編集許可範囲に入っています（AGENTS.md の作業範囲ルール）。 上記のとおりルートの CLAUDE.md だけは入っていません。

7. scripts/speckit（スクリプト層）

スラッシュコマンドの下で動いているのが .specify/scripts/bash/ の 4 本です。 scripts/speckit はそれを呼ぶラッパー CLI で、Claude Code を介さずに手で実行できます。 

scripts/speckit specify "<feature description>" [--short-name <name>] [--number N] [--json]
scripts/speckit plan [--json]
scripts/speckit check [--json] [--paths-only] [--require-tasks] [--include-tasks]
scripts/speckit context [codex|claude|gemini|copilot|cursor-agent|...]
サブコマンド実体用途
specifycreate-new-feature.sh番号付きブランチと specs/<NNN-...>/spec.md を作る
plansetup-plan.sh計画テンプレートを配置する（既存の plan.md を無条件に上書き。節 6）。ブランチ検査あり（節 5）
checkcheck-prerequisites.shどの成果物が揃っているかを確認する。--paths-only は成果物の有無検査だけを飛ばしてパスを出す（ブランチ検査は --paths-only でも走るので、feature/<name> 上では診断に使ったこのコマンド自体が止まる。節 5）
contextupdate-agent-context.sh指定エージェント向けのコンテキストファイルを更新する（codex が既定）

/speckit.taskstoissues は GitHub MCP サーバー経由で issue を作ります （speckit.taskstoissues.md の tools: ['github/github-mcp-server/issue_write']）。 このハーネスは GitHub MCP サーバーを同梱・配線していません（.mcp.json は無く、 settings.local.json は enableAllProjectMcpServers: false）。使うなら接続を別途用意してください。

この書き込みは scm-guard の検査対象外です（止まりません）。 scm-guard はシェルコマンドの文面を正規表現で検査する仕組みで、MCP ツールの呼び出しを一切見ないためです （素の gh issue create のほうも意図的に許可されています）。外向きの操作がガード無しで通るので、 実行前にユーザーの了承を取ってください。

8. 作業の開始と終了（SCM）

/speckit.implement の手順 10 は、実装の前後に SCM の手続きを挟みます （.claude/rules/common/git-workflow.md）。implement は「実装したら終わり」ではありません。

  • 最初の編集の前 — checkout が develop から切った feature/<name> に在ることを確認する。 develop や main に居るなら先に切る（リリース済みコードへの緊急修正なら main から hotfix/<version>）
  • 完了検証の後 — 新しいセッションで /review-pr working を実行する案内を出すまでが完了 （develop との差分。未コミット分も含む）。commit・push・PR はそのレビューの後、それぞれユーザーの了承を得て進める

Perforce 管理下のファイルを触る場合は .claude/rules/common/p4-workflow.md の手順に読み替えます （保留 CL を作ってから編集し、シェルブ後に /review-cl <CL>）。

9. つまずきどころ

症状原因と対処
ERROR: Not on a feature branch. Current branch: feature/xxx節 5。シェルで export SPECIFY_FEATURE=<NNN-short-name> を設定してから Claude Code を起動し直す。/speckit.specify 以外のすべてのコマンドで出る（clarify が最初、check --paths-only でも出る）
計画の Constitution Check が空っぽ / analyze が何も言わないconstitution が未記入。節 2 の /speckit.constitution を先に回す
/speckit.implement や /speckit.analyze が tasks.md が無いと言うどちらも前提検査を --require-tasks 付きで走らせる。/speckit.tasks を先に実行する
ERROR: Multiple spec directories found with prefixspecs/ に同じ 3 桁番号のフォルダーが 2 つある。1 番号 1 フォルダーに整理する
/speckit.specify が意図しない親から分岐したブランチは現在の HEAD から切られる。実行前に develop（または基にしたいブランチ）へ移動する
plan / tasks が別の機能のフォルダーを触っているecho $SPECIFY_FEATURE を確認する。古い値が残っているとエラー無しでそちらの specs/ を対象にする（節 5）。現在の対象は scripts/speckit check --paths-only の FEATURE_DIR で分かる
/speckit.specify の番号が既存と衝突したslash コマンド経路は short-name 単位で番号を数える（speckit.specify.md 手順 2 が [0-9]+-<short-name>$ で検索し --number N+1 を渡す）。新しい short-name なら specs/001-* が在っても 001 から振られる。番号を固定したいなら scripts/speckit specify --number N を直接呼ぶ（slash コマンドに --number を書いても、手順 2 が後ろに付ける値で上書きされる）
番号が飛ぶ / リモートの番号と重なる素の scripts/speckit specify はリモートとローカルのブランチ、および specs/ の全体から最大値 + 1 を取る。ただし create-new-feature.sh は git fetch --all --prune 2>/dev/null || true で取得失敗を黙殺するので、オフライン・認証切れ・プロキシ不通では手元の参照だけで番号が決まり、リモートの番号と衝突しうる（警告も出ない）。確実にしたいなら --number N を渡すか、git fetch が通る状態で実行する
plan.md に書いた内容が消えた/speckit.plan の再実行が plan.md をテンプレートで無条件に上書きする（節 6）。再実行の前に commit するか退避する
