# コーディングスタイル（共通）

> 正本: `.claude/rules/common/coding-style.md`（英語）。
> コメント規約と表記・レイアウト規約は、ソースファイルを読み書きするときだけ読み込まれる別ファイル
> `code-comments.md` / `code-layout.md`（Codex / Antigravity の写しは `common-` 接頭辞）にある。

## 不変性（最重要）

既存オブジェクトを変更（ミューテート）せず、新しい値を返す形を優先する。隠れた副作用を防ぎ、
デバッグを容易にし、安全な並行処理を可能にするため。
例外: エンジン管理下のホットパス（Unity の毎フレーム処理、Unreal のゲームプレイループ）は
エンジン別ルール（`unity/`・`unreal/`）に従う。

## 基本原則

KISS・DRY・YAGNI に従う。頭字語だけからは決まらない 2 点だけ明記する。巧妙さより明快さを
優先すること、そして抽象化は繰り返しが実際に起きてから入れること（先回りしない）。

## ファイル構成

多数の小さいファイルを、種類別ではなく機能・ドメイン別に構成する（高凝集・低結合）。
大きくなったモジュールからはユーティリティを抽出する。
通常 200〜400 行、最大 800 行。

## エラー処理

- 各層でエラーを明示的に処理する。握りつぶさない
- UI 向けコードはユーザーに分かりやすいメッセージ、サーバー側は詳細なコンテキストをログへ

## 入力検証

- すべての入力をシステムの境界で処理前に検証し、失敗は早く・明確なメッセージで検出する
- 可能ならスキーマベースの検証を使う
- 外部データ（API 応答・ユーザー入力・ファイル内容）を信用しない

## 命名規則

- 変数: `camelCase`（説明的な名前）。関数は言語の規則に従う（C#/C++ は `PascalCase`）
- bool 型: `is` / `has` / `should` / `can` を先頭に
- インターフェース・型: `PascalCase`
- 定数: 言語の規約に従う — C++ は `k` + `PascalCase`（`kMaxHealth`）、C# は `PascalCase`、Unity は `k_` + `PascalCase`、Unreal は `PascalCase`、Rust は `SCREAMING_SNAKE_CASE`。`ALL_CAPS` を使うのは Rust だけで、これは Rust 自身の lint が要求するため。C++ では Core Guidelines が `ALL_CAPS` をマクロ名専用としている
- 引数: 接頭辞なしの `camelCase`（`playerId`、`isAlive`）— 各言語の規約が一致している形なので、プロジェクト独自の印は付けない
- フィールド: private / internal のインスタンスフィールドは `_` + `camelCase`（`_playerId`）、static は `s_` + `camelCase`（`s_callCount`）。使用箇所で記憶域とスコープを示すものが他に無いのでこの 2 つだけ印を付ける。ポインターと参照には付けない（型は宣言が示している）。独自の命名を定める言語・エンジンの規約が優先する（`unreal/` は Epic 命名でフィールドの印なし、`rust/` は `self` 経由の `snake_case`）
- ラムダの引数は引数規約の対象外。1 つの式の中だけで使うものなので、変数の規約に従う（`players.Where(player => player.IsAlive)`）
- 列挙定数: 全言語で `PascalCase`。定数の表記には合わせない（`ALL_CAPS` の列挙子は同名のマクロと衝突するため）。**最後のメンバーを必ず上限（件数）として定義する**（`Max`）。switch の網羅性と配列サイズがこれに依存するため、全言語・全エンジンに適用するプロジェクト規約として維持する。Rust だけは `rust/` 規約が述べる例外。型名は `PascalCase` のまま

### 名前の品質

名前はコメントが無くてもそれ自体で役割が伝わるようにする:

| ❌ | ✅ | 理由 |
|----|----|------|
| `int c;` | `int playerCount;` | 略語・1 文字変数は禁止（ループカウンタ `i`、`j` のみ例外） |
| `UserInfo userInfo;` | `UserInfo player;` | 型名の繰り返しは禁止 |
| `bool isNotAlive;` | `bool isDead;` | 否定形の bool 名は禁止 |

- 「どうやるか」ではなく「何をするか」で命名する（`SaveToFile()` ではなく `Save()`）
- 検索処理は `Find` を含める。イベントハンドラーは `On` で始める。非同期関数は `Async` で終わる

## 関数・クラスの設計

- 引数が多い場合は構造体・クラスにまとめる
- 二次元配列のインデックス計算（`cells[y * width + x]`）は関数化する（`GetCell(x, y)`）
- オーバーライドする関数には `override` を明示する
- メンバ変数は最小限に。他のメンバから導出できる値はプロパティ・ゲッターで返す

## 設計原則

SOLID 原則とデメテルの法則に、一般的な定義のまま従う。このプロジェクト固有の点は 1 つだけで、
LINQ / STL のチェーンはデメテルの法則の対象外（同一コレクションの変換であって、別オブジェクトの
内部を辿っていないため）。

## 避けるべきコードスメル

- 深い入れ子 — 入れ子の条件分岐ではなく早期 return（ガード節）を使う
- マジックナンバー — 意味のある閾値・待ち時間・上限値は命名定数に切り出す
- 長い関数 — 責任ごとに分割する

## 品質チェックリスト

- [ ] コードが読みやすく、命名が適切
- [ ] 関数が小さい（50 行未満）
- [ ] ファイルが集中している（800 行未満）
- [ ] 深い入れ子が無い（4 段超え禁止）
- [ ] エラー処理が適切
- [ ] ハードコードされた値が無い（定数・設定を使う）
- [ ] ミューテーションが無い（不変パターンを使用）
