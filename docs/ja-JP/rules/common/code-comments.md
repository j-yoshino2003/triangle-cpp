# コメント規約

> 正本: `.claude/rules/common/code-comments.md`（英語）。
> ソースファイルを読み書きするときだけ読み込まれる（frontmatter の `paths:` による条件読み込み）。
> 常に効く設計方針は `coding-style.md`（Codex / Antigravity の写しは `common-coding-style.md`）にある。

## コメント

プログラム初心者でも理解できる平易な言葉で、「なぜそうするか」が伝わるように書く。

| ルール | 例 |
|------|----|
| 1 行の末尾はピリオド | `// プレイヤー数.` |
| 全角と半角の間に半角スペース | `プレイヤー ID` |
| `-er` / `-or` / `-ar` 語尾は長音符を付ける | Player → プレイヤー |

- 変数・関数の宣言には概要コメントを直上に 1 行
- 関数定義・クラス・構造体・列挙体には XML 形式（`/// <summary>`）
- `// TODO:` はやるべきこと、`// NOTE:` は備忘録・注意書き
- `TODO` / `NOTE` の本文が 2 行以上になる場合は、ラベルの直後で改行し、本文は次の行から書く
- `bool` の**引数と戻り値**は `true = ... 、false = ...` の形で**両方の意味**を書く。
  名前だけでは false のときに何を意味するかが伝わらないため。
  言語ごとの真偽値型（`VkBool32`・`BOOL` など）も対象で、その型のリテラルで書く

```cpp
// ❌ false のときに何が起きるのか読み取れない.
/// <param name="isVisible">表示するかどうか.</param>
/// <returns>有効なら true.</returns>

// ✅ 両方の意味を書く.
/// <param name="isVisible">true = 表示する、false = 隠す.</param>
/// <returns>true = 有効、false = 無効.</returns>
```

```cpp
// ✅ 1 行で済む場合はラベルと同じ行に書く.
// TODO: リトライ回数を設定ファイルへ移す.

// ✅ 2 行以上になる場合は TODO: / NOTE: の直後で改行する.
// TODO:
// リトライ回数を設定ファイルへ移す.
// サーバー側の設定 API が入ってから対応する.
```

### 変更の経緯をコメントに残さない

コメントに書くのは「**なぜ今のコードがこうなっている必要があるか**」だけ。何を変えたか、前はどうだったか、
どの案を採らなかったか、は書かない。それはバージョン管理が持っている情報であり、次の変更が入った時点で
古くなる。

| ❌ | ✅ |
|----|----|
| `// NOTE: 一時的に無効化していたが元に戻した.` | 削除する |
| `// 以前は List を使っていたが遅いので変更.` | `// 要素数が固定なので配列を使う.` |
| `// TODO: 2026/08/16 追加.` | 削除する。日付はログにある |
| `// 修正: #1234 対応.` | `// 負の残量を 0 に丸める. UI が負値を表示できないため.` |

次のものも残さず削除する。

- コメントアウトしたコード — バージョン管理が覚えている
- ファイル冒頭の `// 変更履歴` ブロックや、修正ごとの履歴書き
- 理由の説明が無い、チケット番号だけのコメント

判断基準は「**そのファイルを初めて読む人に、過去の経緯を知らなくても意味が通るか**」。
編集の記録としてしか意味を成さないなら、コードに置く価値はない。書き残す必要が本当にあり、
コードから読み取れない決定は、`.claude/rules/` か該当する `README.md` に書く。
