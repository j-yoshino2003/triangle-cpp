コーディング規約ハーネス — 使い方ガイド

対象: Claude Code（C/C++・C#・Unity・Unreal Engine ／ 完全オフライン動作）

1. これは何?

「仕様を渡す → AI が規約どおりに実装 → 別の AI がレビュー → 直す → 完成」という 開発ループを回すための土台です。コーディング規約・レビューエージェント・チーム開発スキル・ 安全フックが 1 フォルダーに同梱されており、コピーするだけでどのプロジェクトでも同じループが再現できます。

2. セットアップ（新しいプロジェクトに入れる）

  1. AGENTS.md・CLAUDE.local.md・docs/・.claude/ をプロジェクトルートへコピー
  2. Claude Code でフォルダーを開く → ローカルプラグイン（edit-scope-guard / desktop-notify / scm-guard / git-harness / p4-harness）の信頼確認が一度出るので承認（通信は発生しない）。フックはこの 5 プラグインが提供するため、承認しないと編集ガードも SCM ガードも通知も動かない
  3. Perforce 管理下のファイルも扱う場合のみ、環境変数 P4_PROXY に到達可能な Perforce サーバー（ssl:<host>:<port>）を設定する。p4 コマンドはすべてこれ経由で実行され、アドレスはファイルに書かない。Git だけで使うなら p4-harness は何もしない
  4. AGENTS.md の作業範囲リストのプレースホルダーを実際の作業ディレクトリに書き換える（CLAUDE.local.md は AGENTS.md を参照するだけなので触らない）
  5. .claude/vendor/edit-scope-guard/scripts/edit-scope-guard.sh の ALLOW_PATTERNS を手順 4 の一覧と同じ内容にする（Codex / Antigravity も使うなら .codex/scripts/ と .agent/.agents/plugins/coding-harness/scripts/ の同名スクリプトも同じ一覧にする。節 7）
  6. SCM の運用が違う場合は .claude/vendor/scm-guard/scripts/scm-guard.sh の BLOCK_PATTERNS を調整（既定は Perforce の提出・取り消し / git の強制 push・リモートブランチ削除 / gh の書き込み / 公開・デプロイをブロック。通常の git push は許可だが、rules/common/git-workflow.md に従い push 前にブランチ名を示して確認を取る）
  7. 必要なら settings.local.json（モデル・言語・権限）を自分の環境に合わせる。permissions.allow には読み取り系コマンド（ls / grep / git status / dotnet build 等）が登録済みで承認プロンプトが出ません。permissions.deny には scm-guard と同じ禁止コマンドが素の形式で入っており、二段構えの防御になります

3. 開発ループの回し方

ループ A: 不具合修正・機能変更 — 症状か変更内容を渡すだけ。レビューは含まない（ループ C で別セッション） 
/team-change 三角形の頂点色が Rust 版だけ反転して表示される
/team-change ウィンドウのリサイズに追従してスワップチェーンを再生成する
  1. 調査・設計 — 調査担当が根本原因（不具合）または実装方針（機能変更）と影響範囲・対象ファイルを特定し、更新すべき仕様書（specs/<feature>/spec.md）を見つける（読み取り専用）
  2. 仕様書更新 — 実装担当が コードより先に 仕様書を変更後の挙動に書き換える（無ければ .specify/templates/spec-template.md から新規作成）。曖昧なら推測せず質問
  3. 実装 — 実装担当だけがファイルを編集し、仕様書を満たす最小限の変更を入れてビルド・テストまで実行
  4. 責任者チェック — リードが「依頼 → 仕様 → コード」の整合と影響範囲を最終確認。不一致なら差し戻し
  5. 納品と引き渡し — 変更マニュアル（HTML）が生成されて完了。変更は作業ブランチに 未コミットのまま置き、レビューは 新しいセッションで /review-pr working（ループ C）。commit → push → PR はレビューが通ってから、それぞれ了承を得て進める
ループが途中で止まる条件も組み込み済み: 依頼が曖昧なら推測せず質問、根本原因が特定できなければ停止して報告、編集範囲外が必要になったら停止して確認。
ループ B: 自分で書く / 小さな変更 — スキルを使わない日常の回し方
  1. 作業の開始時に Claude が develop から work/<short-name> を切る（rules/common/git-workflow.md の「作業の開始と終了」）
  2. 実装を依頼すると、規約は自動で適用される（節 5）。ビルドが壊れたらエラーメッセージを渡して最小差分で復旧させる
  3. 書き終わったら新しいセッションで /review-pr working（ループ C。未コミット分を含む develop との差分）。指摘を直したら再レビュー
  4. レビューが通ったら commit → push → PR。それぞれ了承を取ってから進める。コミット前のフックが秘密情報・デバッグ残骸・コミットメッセージの形式を検査する
マージ（gh pr merge）は人間の操作。Claude は拒否される。
ループ C: PR・ブランチ・作業ツリーを別セッションでクロスレビュー — ループ A の変更はここでレビューする 
/review-pr 12
/review-pr work/swapchain-resize
/review-pr working

実装したセッションではレビューしません。新しい Claude Code セッションで /review-pr を実行すると、 git-harness のスクリプトが develop との差分（PR 番号なら gh 経由、working なら未コミット分まで）を取得し、 レビューエージェント（code-reviewer / impact-scope-reviewer / silent-failure-hunter / coding-standards-reviewer / comment-analyzer / performance-reviewer / simplicity-reviewer）が独立・並列に検査 → リードが差分突き合わせ検証を行い、CRITICAL / HIGH / MEDIUM / LOW の日本語レポート（docs/reviews/）と判定（APPROVE / WARNING / BLOCK）を出します。 修正が要る場合は同じ作業ブランチで直して再レビューします。マージはユーザー自身の操作です（gh pr merge はガードで拒否されます）。

ループ D: Perforce の保留 CL を別セッションでクロスレビュー — Perforce 管理下のファイルを触ったときだけ使う 
/review-cl 12345
/review-cl 12345 --focus=standards

P4V の保留番号を渡すと、p4-harness のスクリプトがシェルブ済みの差分を取得し、ループ C と同じレビューエージェントが 独立・並列に検査してレポート（docs/reviews/）と判定を出します。完全に読み取り専用で、 ファイル修正も p4 edit / p4 submit / p4 shelve も行いません。指摘の修正は実装セッションで同じ CL に入れ、 /p4-shelve で再シェルブして再レビューします。シェルブされていない CL は差分を読めないため、シェルブを促して停止します。 提出（p4 submit）は人間の操作で、Claude は拒否されます。

補助: Claude Code 自体について調べる 
/ask-claude-code settings.local.json と settings.json の優先順位は?

フック・設定・権限など Claude Code 本体の仕様を、公式ドキュメント参照エージェントが調査して日本語で回答します（調査専用・設定は勝手に変更しない）。

4. ループを守る安全装置

装置働き
編集範囲ガード許可ディレクトリ外への Edit / Write / NotebookEdit を機械的に拒否（プラグイン edit-scope-guard。セットアップ手順 4 で範囲を設定）
SCM ガードPerforce への提出・取り消し（p4 submit / p4 revert）、git のリモート履歴を壊す操作（push --force / push --delete / push --mirror / send-email 等。通常の git push は許可）、gh の状態変更・公開操作（pr merge / release create 等。pr create や issue create は許可）、外部への公開・デプロイをコマンド全文の正規表現で拒否（プラグイン scm-guard。permissions.deny は前方一致のため、オプション付きの形を捕捉できる本フックと併用）
Git 品質フック--no-verify の禁止、コミット前の品質確認、push 前のリマインド、PR 作成後の後処理（プラグイン git-harness。Node.js が必要）
P4 品質フックp4 submit / revert / shelve -d / change -d の拒否、シェルブ前の秘密情報・デバッグ残骸・CL 説明文形式の検査、シェルブ前の確認リマインド、シェルブ後の /review-cl 案内（プラグイン p4-harness。Node.js が必要）
編集者 1 名原則チームループでは実装担当だけが編集し、調査担当は読み取り専用 — ファイル競合を防止
仕様書先行ループ A では specs/<feature>/spec.md を更新してからコードに着手する。仕様書に書けない曖昧さは推測せず質問で解消
レビューの分離実装するセッションはレビューしない。別セッションの /review-pr（PR・ブランチ・working）、Perforce なら /review-cl（シェルブ後）で独立にレビューする
回答方針不確かなことを断定しない・推測だけで答えない（rules/common/answer-policy.md）
toast 通知入力待ち・完了を Windows トーストで知らせる — ループを放置して回せる（プラグイン desktop-notify）

5. 規約はどう効くか

  • .claude/rules/common/ のうち frontmatter の paths: を持たない 4 本（answer-policy・coding-style・git-workflow・p4-workflow）は毎セッション自動読み込み。common/code-comments.md・common/code-layout.md と cpp/・csharp/・rust/・unity/・unreal/ は paths: に一致するファイル（*.rs、Assets/**、Source/** 等）を読み書きする時だけ読み込まれる。条件読み込みになるかを決めるのは paths: の有無だけで、どのディレクトリに置くかは関係ない
  • 優先順位: エンジン別 > 言語別 > 共通
  • 正本は英語（.claude/rules/ と .claude/skills/）。日本語で確認したい時は docs/ja-JP/rules/ と docs/ja-JP/skills/（変更時は英語 → 日本語の順に更新）
  • コミット種別は feat / fix / refactor / docs / test / chore / perf / ci

6. リファレンス

フォルダー構成

プロジェクトルート/
├── AGENTS.md                    # 作業範囲・回答方針・読む規約ファイルの指示・SCM の手順（Claude Code / Codex / Antigravity 共通）
├── CLAUDE.local.md              # AGENTS.md への参照のみ（Claude Code 用の入口）
├── docs/ja-JP/                  # 日本語リファレンス（規約・スキルの翻訳・本ガイド。skills/codex/ と skills/antigravity/ も）
├── .codex/                      # Codex CLI 版（節 7）: config.toml / hooks.json / scripts / rules の複製 / agents / skills
├── .agent/                      # Antigravity CLI 版（節 7）: agents / skills / rules の複製 / .agents/plugins/coding-harness
└── .claude/
    ├── settings.local.json      # 全設定: プラグイン配線・モデル・言語・権限
    ├── rules/                   # 規約（英語・正本）: common / cpp / csharp / rust / unity / unreal
    ├── skills/                  # team-change / git-pr-cross-review / p4-cl-cross-review / ask-claude-code
    ├── commands/                # spec-kit のスラッシュコマンド（speckit.*）
    └── vendor/                  # ローカルプラグイン（フックはすべてここに集約）
        ├── edit-scope-guard/    # 編集範囲ガード（有効）: hooks/hooks.json + scripts/
        ├── scm-guard/           # SCM・公開ガード（有効）: hooks/hooks.json + scripts/
        ├── desktop-notify/      # toast 通知（有効）: hooks/hooks.json + scripts/
        ├── git-harness/         # Git 品質フック・git/GitHub スキル（有効）: hooks/hooks.json + scripts/
        └── p4-harness/          # P4 品質フック・p4-workflow スキル・/p4-shelve /review-cl /p4-status・レビューエージェント（有効）

フックは <プラグイン>/hooks/hooks.json にのみ定義します（settings.local.json の "hooks" ブロックには書かない。両方に書くと合算されて二重実行になります）。 プラグインの読み込みは Claude Code の起動時のみのため、変更後は再起動が必要です。

サブエージェント

このハーネスはレビュアーのサブエージェント 8 体を .claude/vendor/git-harness/agents/ と .claude/vendor/p4-harness/agents/ に同梱しています。/review-pr（スキル git-pr-cross-review）と /review-cl（スキル p4-cl-cross-review）が 独立・並列に呼び出すもので、いずれも読み取り専用です （ファイルの編集・コミット・push・p4 の状態変更は一切しません）。

エージェント役割出番
code-reviewer正しさとセキュリティ（ロジック誤り、null／ライフタイム問題、並行性、呼び出し元への影響範囲、差分内の対応漏れ、資格情報の直書き、インジェクション、パストラバーサル）。低い重大度でコード品質（過大な関数、深いネスト、握り潰した失敗、デバッグ残骸）も見る/review-pr --focus=correctness。既定では常に実行
impact-scope-reviewer差分に含まれていない追随漏れの検出、7 種類（シグネチャは変わらないのに変わった意味、未処理の列挙値、文字列キー／リフレクション／エディタデータ経由の参照、セーブデータ／アセット／設定／通信ペイロードの互換性、二重実装のもう一方、判別ケースのテストの欠落、差分外に残った古い仕様書やマニュアル）。ビルドが落ちる種類は対象外--focus=impact。既定では常に実行
silent-failure-hunter空の catch、不十分なログ、危険なフォールバック、エラー伝播の欠落、エラー処理そのものの欠落の検出--focus=errors。既定では常に実行
coding-standards-reviewer.claude/rules/ の規約（共通 + 変更ファイルに対応する言語・エンジン）との突き合わせ。観点は命名、引数、列挙体、初期化、型推論、制御フロー、空行とレイアウト、コメント、機能グループ区切り、ファイルヘッダー、言語固有のイディオム--focus=standards。既定では常に実行
comment-analyzerコメントの事実としての正確さ、説明の網羅性、長期的な価値（陳腐化。規約が禁じる変更履歴コメントを含む）、誤解を招く記述の点検--focus=comments。既定では常に実行
performance-reviewerその変更が持ち込んだ無駄な処理（計算量・割り当て・コピー・I/O・ロック、および捕捉したスコープを生かし続ける長命オブジェクトの保持）の検出。指摘には発生条件（通る頻度とデータ量）が必須で、それが書けないものは指摘にしない--focus=performance。既定では常に実行
simplicity-reviewer問題より大きい解になっていないかの検出（利用者が 1 つだけの抽象、重複した処理、手書きの再実装、他のメンバーから導ける状態、変更に必要な範囲より広い境界、回りくどい制御）。振る舞いを変えない提案だけを出す--focus=simplicity。既定では常に実行
pr-test-analyzer変更された各経路の振る舞いの網羅、テストの品質、残っている隙の評価--focus=tests を指定したときだけ実行

--focus を付けない既定では上位 7 体が並列で走ります。レビュアー同士は状態を共有せず、 メインセッションが指摘を差分と突き合わせてから docs/reviews/ にレポートを書きます。

これとは別に、調査・設計・汎用の作業は Claude Code 組み込みのエージェントに役割を説明して依頼します （チームループのスキルが内部で使うのもこれらです）。

Plan実装計画の作成複雑な機能・設計判断

7. Codex / Antigravity で使う

同じプロジェクトで OpenAI Codex CLI（.codex/）と Google Antigravity CLI（.agent/）も使えます。 作業ルールは共通の AGENTS.md、規約・スキル・安全装置は Claude Code 版と同じ内容で、各 CLI の仕組みに載せ替えてあります。 取得スクリプト（.claude/vendor/git-harness/scripts/review-target.sh、.claude/vendor/p4-harness/scripts/）は bash なので 3 つで共用します。

セットアップ（Claude Code 版に追加で）

  1. .codex/（Codex）／ .agent/（Antigravity）をプロジェクトルートへコピー。AGENTS.md は共通なので 1 つ
  2. Codex: そのフォルダーで codex を起動してプロジェクトの信頼確認を承認する（未承認だと .codex/ の設定・フック・サブエージェントが読み込まれない）。必要なら .codex/config.toml のモデル・推論強度を変える
  3. Antigravity: そのフォルダーで CLI を起動する。.agent/skills/ はスラッシュコマンドに自動変換され、プラグイン .agent/.agents/plugins/coding-harness/ のフックが有効になる
  4. 編集範囲ガードは CLI ごとに別のフックなので、ALLOW_PATTERNS を 3 箇所（.claude/vendor/edit-scope-guard/scripts/・.codex/scripts/・.agent/.agents/plugins/coding-harness/scripts/ の edit-scope-guard.sh）とも AGENTS.md の一覧に揃える
